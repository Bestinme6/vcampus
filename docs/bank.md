# 虚拟银行使用与验收说明

## 功能与角色

学生和教师进入银行时按需创建一个余额为 `0.00` 的虚拟账户，可以查看余额、向启用用户转账并查询本人流水。银行管理员和超级管理员额外拥有账户检索、充值、冻结、解冻及全量流水查询权限；充值、冻结、解冻和流水筛选均填写目标用户名（学生账号即学号），由服务端解析实际用户 ID。所有身份与权限由应用服务器根据会话判断，客户端不连接 MySQL，也不能通过伪造用户 ID 操作他人账户。

## 页面

JavaFX “我的校园”的余额概览使用 `bank.account.summary`，只读查询本人已有账户。返回 `opened=false` 时显示“未开户”，不写入账户或流水；进入银行业务页仍由原有 `bank.account.get` 按需开户。该只读动作同样经过服务端会话、首次改密和角色检查。

- 默认 JavaFX 普通用户导航：账户总览、校园转账、资金流水；总览使用余额卡、隐藏余额、冻结提示、快捷入口及最近五条流水，不再使用个性化问候或整页表格。
- T1 转账独立分为填写、核对、结果三步；核对前通过只读接口查询启用收款人的显示名，实际扣款仍由服务器重新验证。没有用户填写的转账备注。
- 管理员额外导航：账户管理、全量流水。选中或核对精确账号后办理充值、冻结、解冻，均需二次确认。未开户用户也可按账号核对；核对本身不开户。
- 流水使用卡片列表与详情，支持类型、日期、关键字、业务编号及分页；收支汇总来自服务端完整筛选结果，不是本页相加。本人流水和管理员全量流水明确分离。
- 消息中心的银行通知直接打开原生“资金流水”；本人商店支付、退款详情可打开所属订单，全量流水不提供跨用户订单入口。
- 所有 Socket 请求在后台线程执行，JavaFX 页面在 FX 线程更新。查询期间禁用内容区，但可离开页面；过期查询不能覆盖新页面，登出会关闭本次会话控制器。
- 旧 Swing 客户端及原接口仍保留；旧页面更新继续使用 Swing 事件线程。

## 交易结果待确认

转账和充值每次确认生成不可变的目标、金额及 UUID。提交期间不能重复提交；网络超时、数据库异常或畸形回执不会被显示成确定失败。离开银行再回来仍保留本会话的待确认操作，重试复用原编号及参数。

如果首次结果未知，重试被业务拒绝也不能证明首次未入账；界面仍保留“结果待确认”，允许查询原业务流水。仅匹配相同编号、金额、类型和查询账户范围的流水才能确认成功。待确认信息不跨登出持久保存；登出后应先核对流水，不能直接重新发起同额操作。

## 增量协议（向后兼容）

- `bank.recipient.get`：精确 `recipientUsername`，返回 `username/displayName/self`，不返回余额、不创建账户。
- `bank.ledger.search`：新增 `scope=mine|admin`、`keyword`、`fromDate`、`toDate`、`referenceNo`。普通账号始终只查本人；管理员传 `mine` 时也强制本人。未传 scope 的旧客户端沿用原范围规则。
- 日期采用上海时区自然日，起止日均包含；关键字按字面匹配描述或业务编号，转义 SQL 通配符。
- 返回增加 `income/expense` 全结果汇总，既有 11 字段流水行编码不变。
- `bank.ledger.order`：按 `referenceNo` 查询本人已关联支付/退款流水的订单，由服务端会话决定所有者，不接受客户端声明的用户 ID。

此次银行升级只增加查询和界面，不修改数据库结构；已有数据库仍需具备原银行及商店表。

## 资金规则

- 金额由 MySQL `DECIMAL(15,2)` 和 Java `BigDecimal` 保存，不使用浮点数；
- 转账和充值只接受大于零、最多两位小数、非科学计数法且不超过 `9999999999999.99` 的金额；
- 转账按账户 ID 固定顺序加锁，并在持锁后再次检查余额，两个并发请求不能造成透支；
- 每次转账或充值使用 UUID 业务编号，数据库唯一约束防止重试造成重复入账；
- 充值、冻结或解冻前必须确认目标用户存在且已启用，否则返回“目标用户不存在或已停用”，不创建账户、不写流水或通知；
- 流水只能新增，应用不提供修改或删除历史流水的接口；
- 冻结账户可以查看、收款和接收商店退款，但不能主动转账或支付；
- 余额变更、流水和通知在同一个 JDBC 事务中提交或回滚。

流水类型包括管理员充值 `ADMIN_TOPUP`、转账支出 `TRANSFER_OUT`、转账收入 `TRANSFER_IN`、商店支付 `SHOP_PAYMENT` 和商店退款 `SHOP_REFUND`。商店后续通过服务端的 `BankPaymentWriter` 复用同一数据库事务，不能从客户端补发第二次扣款请求。

## 消息中心联动

| 事件 | 接收人 | 类型 | 跳转 |
| --- | --- | --- | --- |
| 他人转账成功 | 收款人 | `BANK_TRANSFER_RECEIVED` | `BANK_LEDGER` |
| 管理员充值成功 | 目标用户 | `BANK_ACCOUNT_TOPPED_UP` | `BANK_LEDGER` |
| 账户实际冻结或解冻 | 目标用户 | `BANK_ACCOUNT_STATUS_CHANGED` | `BANK_LEDGER` |

用户主动操作不通知自己；同一充值或转账业务重试不会重复入账或重复通知，状态没有变化时也不重复通知。消息不包含密码、数据库凭据或其他敏感信息。

## 环境和数据库

服务端读取以下环境变量：

```powershell
$env:VCAMPUS_DB_URL = 'jdbc:mysql://127.0.0.1:3306/vcampus?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai'
$env:VCAMPUS_DB_USER = '你的数据库用户名'
$env:VCAMPUS_DB_PASSWORD = '你的数据库密码'
```

全新数据库依次执行 `database/schema.sql` 和 `database/seed.sql`。旧数据库先备份，再执行 `database/migrations/007_bank.sql`，最后执行最新 `database/seed.sql`。脚本不包含数据库密码或真实个人数据。

银行种子数据依赖匿名演示账号 `2026000001`、`2026000002` 和 `T0000001`。如果账号尚未创建，先通过超级管理员的账号管理创建，再重跑 `seed.sql`。固定种子业务编号和事务保证脚本重复执行不会使余额翻倍。

## 手工验收

1. 启动 MySQL 和应用服务器，再打开两个普通客户端与一个银行管理员客户端；
2. 普通用户首次进入银行，确认自动开户且只能看到三个普通导航；余额卡可隐藏，标题为“账户总览”；
3. 管理员用用户 A 的用户名（学生账号即学号）充值，确认余额、充值流水和消息同时出现；再输入不存在或已停用的账号，确认显示可读提示且没有任何资金数据写入；
4. 用户 A 填写用户 B 和金额，核对页确认真实显示名与金额，提交后查看回执；确认两边余额与成对流水正确，B 收到通知且 A 不收到自通知；
5. 重复提交同一个业务编号，确认余额和流水不重复变化；
6. 冻结 A，确认 A 不能转账，但仍能接收 B 的转账；解冻后恢复转账；
7. 普通用户尝试调用管理员动作应被服务端拒绝；
8. 管理员在“全量流水”留空用户名查看全部流水，填写用户名或学号时只查看该用户；
9. 从三类银行通知详情进入页面，确认直接进入原生“资金流水”；从本人商店付款/退款流水打开对应订单；
10. 连续执行两次 `seed.sql`，确认三个演示账户的种子余额不增加第二次。
11. 组合日期、类型与关键字筛选并翻页；确认汇总覆盖完整结果，管理员切回“资金流水”时只能看到本人记录。
12. 在演示环境模拟转账响应中断，确认显示“结果待确认”；切页返回后使用原编号重试，核对仅一笔扣款。

本任务不替用户启动服务端或改动本机 MySQL。MySQL 多客户端场景需在用户按上述步骤启动环境后人工联调。
