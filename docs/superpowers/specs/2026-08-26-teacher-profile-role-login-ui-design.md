# VCampus 身份体系、教师信息与工作台设计

## 目标

在开发超级管理员账号管理前，先统一 VCampus 的身份、附加管理角色、工作台展示和基础认证规则，并完成教师个人信息功能。本阶段同时修复用户名大小写不敏感以及查询、刷新按钮文字过浅的问题。

## 身份与角色模型

### 基础身份

每个账号必须且只能拥有以下一个基础身份：

- `STUDENT`：学生；
- `TEACHER`：教师；
- `SUPER_ADMIN`：超级管理员。

基础身份之间互斥。任何账号都不能同时是学生和教师，也不能在拥有超级管理员身份的同时拥有学生或教师身份。

### 附加管理角色

业务管理员是基础身份之外的附加角色：

- `STUDENT_ADMIN`：学籍管理员；
- `ACADEMIC_ADMIN`：教务管理员；
- `LIBRARY_ADMIN`：图书管理员；
- `SHOP_ADMIN`：商店管理员；
- `BANK_ADMIN`：银行管理员；
- `FORUM_ADMIN`：论坛管理员。

允许的角色组合如下：

| 基础身份 | 可附加的管理角色 |
| --- | --- |
| 学生 | 图书管理员、论坛管理员，可同时兼任 |
| 教师 | 六种业务管理员，可同时兼任全部六种 |
| 超级管理员 | 不附加任何业务管理员角色 |

教师即使同时兼任全部六种业务管理员，也不等同于超级管理员。业务管理员只拥有对应业务模块的管理权限，不能创建账号、分配角色、停用账号、重置他人密码、管理超级管理员或查看系统级审计记录。超级管理员拥有这些系统级权限。

### 校验边界

共享模块提供唯一的角色组合校验器。服务端在以下边界重复使用它：

1. 创建账号；
2. 修改角色；
3. 登录并建立会话。

登录时再次校验，可以阻止数据库中的历史脏数据绕过规则。非法组合拒绝登录、记录审计结果并提示用户联系超级管理员。客户端只根据服务端返回的角色展示界面，不承担最终授权职责。

## 工作台设计

### 实现方式

使用统一的工作台卡片解析器，根据基础身份和附加角色计算卡片顺序、图标文字、黑体名称、说明和目标页面。避免为不同身份复制三套工作台代码。

### 超级管理员

工作台固定显示六张业务卡片：

1. `学`——学籍管理；
2. `教`——教务管理；
3. `书`——图书管理；
4. `商`——商店管理；
5. `银`——银行管理；
6. `论`——论坛管理。

所有黑体名称删除“虚拟”二字。超级管理员的“账号与角色管理”放在左侧导航栏，不占用六张业务卡片，并且只有超级管理员可见。

### 学生

普通学生固定显示六张卡片：

1. `学`——学籍信息；
2. `教`——课程安排；
3. `书`——图书借阅；
4. `商`——商店购物；
5. `银`——线上银行；
6. `论`——校园论坛。

如果学生兼任图书管理员，则“书”卡片名称改为“图书管理”；如果兼任论坛管理员，则“论”卡片名称改为“论坛管理”。学生可以同时兼任两个角色，两张卡片可同时切换为管理名称。

### 教师

普通教师固定显示六张卡片：

1. `师`——教师信息；
2. `教`——教学管理；
3. `书`——图书借阅；
4. `商`——商店购物；
5. `银`——线上银行；
6. `论`——校园论坛。

附加角色改变对应卡片：

- 教务管理员：`教`——教务管理；
- 图书管理员：`书`——图书管理；
- 商店管理员：`商`——商店管理；
- 银行管理员：`银`——银行管理；
- 论坛管理员：`论`——论坛管理。

教师兼任学籍管理员时，在最前面增加 `学`——学籍管理，完整顺序为 `学、师、教、书、商、银、论`。

### 布局与滚动

工作台卡片容器放入滚动面板：

- 六张卡片保持当前整齐布局；
- 七张卡片保持相同卡片尺寸并允许向下滚动；
- 不通过缩小文字或压缩卡片来塞入第七张卡片。

## 教师个人信息

### 数据库

新增 `teacher_profiles` 表：

| 字段 | 用途 |
| --- | --- |
| `id` | 教师档案主键 |
| `user_id` | 唯一关联 `users.id` |
| `teacher_number` | 唯一教师工号 |
| `full_name` | 姓名 |
| `department_id` | 所属学院，关联 `departments.id` |
| `professional_title` | 职称 |
| `phone` | 电话 |
| `email` | 邮箱 |
| `created_at`、`updated_at` | 创建和更新时间 |

教师档案不保存密码或角色。认证和授权仍由 `users` 与 `user_roles` 负责。

### 页面与权限

教师点击“师·教师信息”后看到教师工号、姓名、学院、职称、电话和邮箱。

- 教师工号、姓名、学院和职称只读；
- 教师本人可以修改电话和邮箱；
- 查询和修改根据当前会话的用户编号定位档案，客户端不能指定其他教师；
- 没有教师身份的用户不能调用教师档案服务；
- 数据库和 Socket 操作在 Swing 事件线程之外运行，界面更新回到事件线程。

### Socket 动作

共享协议新增：

- `profile.teacher.getSelf`：读取当前教师档案；
- `profile.teacher.updateContact`：修改当前教师的电话和邮箱。

继续使用现有 `RequestMessage`、`ResponseMessage` 和 `MessageCodec`，客户端不直接连接 MySQL。

## 用户名大小写

MySQL 当前数据库排序规则 `utf8mb4_0900_ai_ci` 中的 `ci` 导致普通字符串比较不区分大小写。

设计采用两层处理：

1. 保留用户名唯一索引现有的不区分大小写行为，禁止创建 `admin` 与 `ADMin` 这类仅大小写不同的重复账号；
2. 登录查询使用精确大小写比较，认证服务再用 Java `String.equals` 对请求用户名和存储用户名进行防御性校验。

因此，数据库中存在 `admin` 时，只有 `admin` 能登录，`ADMin` 返回与密码错误相同的“账号或密码错误”，避免泄露账号存在状态。

## 查询与刷新按钮

新增统一的工具栏命令按钮样式：

- 深色粗体文字；
- 浅蓝色背景；
- 清晰边框；
- 启用和禁用状态均可辨认；
- 主动设置不透明和内容区域填充，减少 Windows Swing 外观忽略背景色造成的差异。

所有业务页面中的“查询”和“刷新”按钮使用该样式。登录主按钮和普通新增、编辑、保存按钮不受本次调整影响。

## 数据流与错误处理

1. 客户端携带会话令牌发送请求；
2. 服务端读取会话中的用户编号和角色；
3. 服务端使用统一角色规则进行授权；
4. 仓储层通过参数化 SQL 访问 MySQL；
5. 服务端返回统一响应，客户端在事件线程更新界面。

主要错误处理：

- 教师角色没有教师档案：提示“未找到教师档案，请联系管理员”；
- 非教师访问教师档案：返回“无权执行此操作”；
- 非法角色组合：拒绝账号创建、角色修改或登录；
- 电话或邮箱格式非法：拒绝保存并说明具体字段；
- 用户名大小写不匹配：统一返回“账号或密码错误”；
- 网络或数据库异常：保持现有失败响应机制，不在客户端显示技术堆栈。

## 测试与验收

1. 基础身份测试：每个账号恰好一个基础身份；
2. 学生角色测试：只允许图书和论坛管理员，并允许同时兼任；
3. 教师角色测试：允许附加任意或全部六种业务管理员；
4. 超级管理员测试：禁止附加其他身份和业务管理员；
5. 权限测试：全业务管理员教师仍无账号与角色管理权限；
6. 工作台测试：验证三种基础身份和各管理角色组合的图标、名称、顺序及目标页面；
7. 滚动布局测试：学籍管理员教师显示七张卡片并可滚动；
8. 教师档案测试：读取完整字段，只允许本人修改电话和邮箱；
9. 登录测试：`admin` 成功时，`ADMin` 必须失败；
10. 按钮检查：所有查询和刷新按钮使用深色粗体且在 Windows 外观下清晰；
11. 根目录执行 `mvn clean verify`；
12. 更新 `database/schema.sql`、`docs/requirements.md`、认证、学籍和教务说明。

## 开发顺序

第一阶段实现本设计：身份规则、动态工作台、教师档案、大小写登录和按钮可读性。第二阶段再开发超级管理员左侧导航中的“账号与角色管理”，并复用本阶段的角色组合校验器；创建教师账号时在同一事务中创建用户、角色和教师档案。
