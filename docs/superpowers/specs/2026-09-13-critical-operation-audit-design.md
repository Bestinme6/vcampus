# 关键业务操作统一审计与横排详情设计

## 背景与目标

系统管理的审计页当前只读取 `audit_logs`。认证、账户、图书和系统配置已经写入该表，但银行、商店、教务和论坛主要依赖各自的业务流水或管理日志，导致统一审计页无法回答“谁执行了关键业务变更、结果如何”。同时，审计记录详情使用较小的多行文本框，需要滚动才能看完。

本次改动在保留领域流水作为业务凭证的前提下，为关键写操作补充统一审计摘要，并把详情区替换为无需内部滚动的横向字段布局。

## 方案选择

采用业务服务显式审计，而不是请求路由统一拦截或数据库触发器。

- 服务层知道操作是否真正成功、当前操作者及失败类别，可以写出稳定的动作码和结果码。
- 路由层只负责分派，无法可靠区分业务冲突、参数错误和数据库错误，也容易把只读请求记入审计。
- 数据库触发器拿不到会话语义和协议动作码，不适合当前 MySQL → 服务端 → 客户端的三层结构。

所有模块继续复用 `AuditStore`。审计写入保持 best-effort：领域事务和领域流水仍是业务事实来源；统一审计写入失败记录服务端错误，但不把已经成功的资金、订单或教务事务回滚成客户端失败。

## 统一审计范围

只记录有业务状态变化或管理风险的动作。查询、列表、详情、刷新、预览、收件箱已读状态和购物车临时编辑不进入统一审计。

### 银行

- `bank.transfer.create`
- `bank.admin.topup`
- `bank.admin.freeze`
- `bank.admin.unfreeze`

银行账本继续作为金额、余额和幂等结果的权威记录；统一审计仅补充操作者、动作和结果。

### 商店

- `shop.checkout`
- `shop.buyNow`
- `shop.order.cancel`
- `shop.order.confirm`
- `shop.admin.product.save`
- `shop.admin.product.setEnabled`
- `shop.admin.inventory.adjust`
- `shop.admin.order.ship`

订单、订单明细和库存变更表继续保存业务细节。

### 教务

- 培养方案：创建、修改、复制、发布、归档，及课程条目的新增、修改、删除
- 课程：创建、修改
- 教学班：创建、状态变更、删除、招生范围保存
- 排课：草稿保存、草稿重置、发布
- 学生选课：选课、退课、换班
- 成绩：保存、发布

沿用现有 `academic.*` 动作码，不新增同义动作。

### 论坛

- `forum.post.delete`
- `forum.comment.delete`
- `forum.admin.section.save`
- `forum.admin.section.setEnabled`
- `forum.admin.post.moderate`
- `forum.admin.comment.moderate`
- `forum.admin.report.resolve`

普通发帖、评论、点赞、收藏和举报提交不进入统一审计；论坛举报和审核表继续保存审核理由及目标内容。

### 消息中心边界

当前消息协议只有查询、查看、已读、未读、全部已读和个人删除，没有管理员手工发布或撤回接口。本次不记录这些高频个人状态。由银行、商店、教务或论坛关键操作产生的业务通知，通过源操作的统一审计记录体现。

## 结果码与失败处理

关键操作至少记录以下稳定结果：

- `SUCCESS`：业务状态已经改变或幂等请求得到成功结果。
- `DENIED`：会话有效但角色或资源权限不足。
- `INVALID`：参数格式或业务规则不满足。
- `NOT_FOUND`：目标资源不存在。
- `CONFLICT`：状态冲突、余额/库存/容量不足或重复业务操作。
- `DATABASE_ERROR`：数据库操作失败。

每个服务通过一个小型私有审计辅助方法消除重复，但动作白名单和结果映射仍由业务服务显式控制。已存在的领域异常继续转换为当前客户端提示，不改变协议成功/失败语义。

会话能够解析时记录当前用户编号；会话无效时不创建无主体的业务审计记录，认证失败仍由认证模块单独负责。新增模块暂不扩展 `audit_logs` 表结构，客户端地址沿用这些服务现有的空值行为。

## 依赖与数据流

`VCampusServer` 创建唯一的 `AuditRepository`，并将同一个 `AuditStore` 注入 `AcademicService`、`BankService`、`ShopService`、`ForumService` 和 `ForumReportService`。

一次关键操作的数据流为：

1. `RequestRouter` 按现有动作码把请求交给业务服务。
2. 业务服务完成会话和权限校验。
3. 领域仓储执行原有事务并生成原有流水或管理日志。
4. 业务服务根据最终结果调用 `AuditStore.record(userId, action, result, null)`。
5. 系统管理审计查询按原有分页和筛选读取新记录。

不改变客户端到服务端的长度前缀协议，不让客户端连接数据库，也不增加新的公共协议动作。

## 横排记录详情

删除审计页底部的只读 `TextArea`，改为固定的只读详情面板。面板使用两行、每行四组的横向字段布局：

- 第一行：审计编号、用户编号、用户名、显示名
- 第二行：动作、结果、客户端地址、创建时间

每组包含短标题和完整值标签。详情面板没有 `ScrollPane`、滚动条或文本输入控件；长动作码允许标签自然扩展，并通过 Tooltip 保留完整内容。宽屏保持四列，窗口变窄时列宽按比例收缩并允许值换行，不引入内部滚动。

未选择记录时各值统一显示 `—`。切换选择或刷新结果时同步更新全部八个值。

## 测试策略

严格按测试驱动开发执行：先添加失败测试并确认因缺少审计或旧详情控件而失败，再写最小实现。

- 服务单元测试：每个模块至少覆盖一个成功关键操作会写审计、一个失败关键操作写正确结果、一个只读操作不写审计。
- 接线测试：验证生产服务构造器共享同一 `AuditStore`，现有路由仍返回原业务响应。
- UI 测试：验证详情区不再是 `TextArea` 或滚动容器；选择记录后八个横排字段显示正确；清空选择恢复占位符。
- 回归测试：运行涉及服务的聚焦测试，再执行根目录 `mvn clean verify`。

## 明确不做

- 不把统一审计表改造成银行、订单或论坛审核的完整业务流水。
- 不记录普通查询、列表加载、页面刷新、购物车数量变化、点赞或已读状态。
- 不增加审计记录删除或修改能力。
- 不在本次增加管理员消息发布功能。
- 不修改用户当前主工作区中未提交的登录界面文件。
