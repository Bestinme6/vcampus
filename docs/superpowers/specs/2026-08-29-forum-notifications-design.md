# VCampus 论坛通知联动设计

日期：2026-08-29  
状态：已实现，待本机 MySQL 双客户端验收  
范围：论坛评论、管理员审核通知，以及消息中心到指定帖子的深链

## 1. 目标与边界

论坛中的重要状态变化应进入现有消息中心，使内容作者能够及时获知他人评论和管理员操作，并从消息详情直接打开关联帖子。实现继续遵守现有三层架构：Swing 客户端只通过 Socket 协议访问服务端，论坛数据与通知数据只由服务端通过 JDBC 修改。

本轮包含：

- 他人评论帖子后通知发帖人；
- 管理员对帖子执行所有审核动作后通知发帖人；
- 管理员隐藏或恢复评论后通知评论作者；
- 消息中心增加论坛来源筛选和论坛消息详情；
- 论坛消息可直接打开关联帖子；
- 论坛业务变更、审核日志和通知在同一事务内保持一致。

本轮不包含评论聚合、邮件或短信、桌面系统通知、消息撤回、用户自定义免打扰、点赞收藏通知和后台事件队列。

## 2. 已确认的产品规则

### 2.1 评论通知

每一条成功创建的评论对应一条独立通知。评论者不是帖子作者时，系统通知帖子作者；用户评论自己的帖子时不产生通知。通知发送人是评论者，关联实体是帖子 ID。

通知标题为“您的帖子收到一条新评论”。正文包含评论者显示名、帖子标题和经过长度限制的评论摘要，例如：

> 张三评论了您的帖子《校园活动建议》：评论内容摘要……

### 2.2 帖子管理通知

管理员对帖子成功执行以下任一动作后通知发帖人：

- 隐藏、恢复；
- 锁定、解锁；
- 置顶、取消置顶；
- 设为精华、取消精华。

管理员操作自己发布的帖子时不发送自通知。状态没有变化、内容不存在、权限不足或并发冲突时不产生通知。

通知标题为“您的帖子状态已更新”。正文包含管理员显示名、帖子标题和中文动作名称。隐藏与恢复操作还必须展示管理原因；其他动作使用已有的默认管理原因，不要求用户额外输入。

### 2.3 评论管理通知

管理员成功隐藏或恢复评论后通知评论作者。管理员处理自己的评论时不发送自通知。通知关联到评论所属帖子，而不是评论 ID，以便消息中心可以打开现有帖子详情页。

通知标题为“您的评论状态已更新”。正文包含管理员显示名、帖子标题、中文动作名称和管理原因。

### 2.4 删除行为

作者自己删除帖子或评论不产生通知。当前管理员内容管理使用隐藏与恢复，不新增物理删除或独立的管理员删除通知。

## 3. 公共通知词汇

在 `vcampus-common` 中扩展现有枚举：

- `NotificationSource.FORUM`；
- `NotificationTarget.FORUM_POST`；
- `NotificationType.FORUM_POST_COMMENTED`；
- `NotificationType.FORUM_POST_MODERATED`；
- `NotificationType.FORUM_COMMENT_MODERATED`。

所有现有枚举值保持不变。论坛通知继续使用现有通知查询、分页、详情、已读和未读计数协议，不新增论坛专用通知接口。

## 4. 数据库设计与迁移

继续复用 `notifications` 表，不新增业务表。修改 `database/schema.sql` 中以下检查约束：

- `chk_notification_type` 增加三种论坛通知类型；
- `chk_notification_source` 增加 `FORUM`；
- `chk_notification_target` 增加 `FORUM_POST`。

新增 `database/migrations/006_forum_notifications.sql`，用于已有数据库删除并重新创建上述三个具名检查约束。迁移不得删除现有通知数据。

论坛通知的 `related_entity_id` 始终保存帖子 ID。`sender_user_id` 对评论通知保存评论者 ID，对管理员通知保存管理员 ID；接收人始终是内容作者。

通知标题受表字段 160 字符限制，正文受 1000 字符限制。服务端使用统一的长度限制工具构造论坛通知，帖子标题和评论摘要超长时截断并添加省略号，不能让通知文案导致论坛业务事务失败。

## 5. 服务端事务设计

采用事务内写通知方案。`ForumRepository` 接收 `NotificationWriter` 依赖，生产环境由 `VCampusServer` 将现有 `NotificationRepository` 注入；测试可注入受控实现。

### 5.1 创建评论

`createComment` 锁定帖子时同时读取帖子作者和标题。在同一事务中：

1. 校验帖子正常、未锁定且板块启用；
2. 插入评论；
3. 刷新帖子评论数和最后评论时间；
4. 当评论者与帖子作者不同时插入评论通知；
5. 提交事务。

任何一步失败都回滚评论、统计和通知。

### 5.2 管理帖子

帖子锁定查询应返回作者、标题和当前状态。状态更新成功后，在同一事务中先写审核日志，再在管理员与作者不是同一用户时写通知，最后提交。

八种管理动作统一映射为中文文案：隐藏、恢复、锁定、解锁、置顶、取消置顶、设为精华、取消精华。

### 5.3 管理评论

评论锁定查询应返回评论作者、所属帖子 ID 和帖子标题。评论状态更新、帖子评论统计刷新、审核日志和通知在同一事务内执行。管理员与评论作者相同时跳过通知。

## 6. 客户端消息中心设计

消息中心来源筛选增加“论坛通知”。消息卡片和详情页将 `NotificationSource.FORUM` 显示为“校园论坛”。

消息详情中，合法的 `FORUM_POST` 目标且 `relatedEntityId` 为正数时显示“查看帖子”按钮。为避免丢失帖子 ID，通知导航回调从只传 `NotificationTarget` 调整为传递一个包含 `target` 与 `relatedEntityId` 的客户端导航对象。现有教务、学籍和图书馆目标继续使用同一对象，行为保持不变。

点击“查看帖子”时：

1. 关闭消息详情对话框；
2. 主窗口复用或延迟创建现有 `ForumModulePanel`；
3. 调用 `openPost(postId)` 打开帖子详情；
4. 消息按现有流程保持已读，刷新未读角标。

帖子正常或仅锁定时可以打开。帖子已隐藏或删除且当前用户无权查看时，现有论坛接口返回不可访问，客户端显示“该帖子当前不可访问”并返回论坛首页。具有论坛管理权限的用户仍可打开隐藏帖子。通知历史不随关联内容删除或隐藏而删除。

若论坛通知缺少合法帖子 ID，详情页不显示跳转按钮，但仍可阅读通知正文。

## 7. 错误处理与一致性

- 通知写入失败：论坛业务事务整体回滚，客户端收到通用数据库失败提示；
- 论坛操作失败、无变化或冲突：不写审核成功通知；
- 关联帖子后来不可访问：通知保留，点击后给出可读提示；
- 长标题和长评论：服务端安全截断通知文案，不修改原论坛内容；
- 重复请求：只在数据库状态真正变化并成功提交时生成通知；
- 自操作：接收人与发送人为同一用户时跳过通知。

## 8. 测试与验收

自动化测试至少覆盖：

- 新枚举和 MySQL 检查约束一致；
- 他人评论产生一条通知，自己评论不产生通知；
- 通知失败时评论、统计和通知整体回滚；
- 八种帖子管理动作生成正确通知；
- 管理员操作自己的帖子不产生通知；
- 评论隐藏与恢复通知评论作者；
- 管理员操作自己的评论不产生通知；
- 失败、无变化和并发冲突不产生通知；
- 文案截断后满足通知字段长度；
- 消息中心提供论坛来源筛选和中文来源名称；
- 通知导航保留并使用正确帖子 ID；
- 关联帖子不可访问时返回论坛首页并显示提示；
- 根目录 `mvn clean verify` 通过。

人工验收使用两个客户端：普通用户 A 发布帖子，普通用户 B 评论，A 在消息中心收到未读论坛通知并直接打开帖子；管理员对 A 的帖子依次执行八种动作并对 B 的评论执行隐藏与恢复，对应作者应收到消息。验证自评论、自管理、失败操作不产生通知，并确认未读角标、来源筛选、详情文案和帖子深链正确。
