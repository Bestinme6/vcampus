# VCampus 数据库自动重建与 GitHub 交付设计

**日期：** 2026-09-07  
**状态：** 待书面复核  
**适用项目：** VCampus

## 1. 背景与问题

VCampus 当前要求使用者先手动执行 `database/schema.sql`，已有数据库还要按顺序补执行 `database/migrations/` 中尚未应用的脚本。代码更新包含数据库结构变化时，同学即使成功拉取最新代码，也可能因为本地 MySQL 表结构过旧而遇到服务端异常或界面功能失效。

本次交付面向已经安装并运行 MySQL、且已有 `vcampus` 数据库的同学。用户已确认本地旧业务数据不需要保留，因此设计优先保证“拉取代码后直接启动服务端即可获得与代码匹配的数据库”，不承担旧数据迁移兼容成本。

## 2. 目标与非目标

### 2.1 目标

- 服务端启动前自动判断当前数据库是否与随服务端发布的完整 SQL 脚本一致。
- 数据库一致时不执行任何破坏性操作，正常启动服务端。
- 数据库缺失版本标记或脚本校验值不一致时，自动重建 VCampus 自有表并导入演示数据。
- 自动重建失败时禁止 Socket 服务启动，并输出可定位的中文错误。
- 多个服务端进程同时启动时只允许一个进程执行重建。
- 继续通过环境变量读取 MySQL 地址、用户名和密码，不向 Git 提交口令。
- 将完整 SQL 脚本打包进服务端产物，避免源码目录和运行目录不同导致找不到脚本。
- 将已验证的代码提交到 `https://github.com/Bestinme6/vcampus.git`，但在实际推送前再次取得用户确认。

### 2.2 非目标

- 不保留旧数据库中的账号、课程、成绩、商品、帖子或其他业务数据。
- 不让 Swing/JavaFX 客户端直接连接 MySQL。
- 不将 MySQL 替换为嵌入式数据库，也不强制同学安装 Docker。
- 不自动安装 MySQL、创建 MySQL 用户或写入数据库密码。
- 不提交 `vcampus-server/data/` 下的运行时商品图片。
- 不把现有历史迁移脚本改造成可跨任意旧版本保留数据的迁移链。

## 3. 采用方案

采用“启动前校验脚本指纹，失配时重建 VCampus 自有表”的方案。

服务端把规范来源固定为根目录的 `database/schema.sql` 与 `database/seed.sql`。构建时这两个文件被复制到服务端 classpath。运行时计算二者内容的 SHA-256 组合指纹，并与数据库元数据表中上次成功安装的指纹比较：

- 指纹一致：跳过初始化。
- 元数据表不存在、元数据不完整或指纹不同：重建并重新播种。
- 重建中途失败：不写入成功指纹，服务端退出；下次启动重新尝试完整重建。

与只记录人工递增版本号相比，脚本指纹能避免开发者修改 SQL 后忘记更新版本号。与 Flyway 的保留数据迁移相比，本方案更符合“旧数据无所谓”的约束，能够可靠处理同学数据库处于任意历史状态的情况。

## 4. 架构边界与组件

三层架构保持不变：

```text
MySQL
  ↑ JDBC
DatabaseBootstrapper → VCampusServer → Socket / MessageCodec → Swing 或 JavaFX 客户端
```

新增职责全部位于 `vcampus-server`：

- `DatabaseBootstrapper`：获取互斥锁、读取数据库状态、比较指纹、编排重建并记录成功状态。
- `SqlScriptLoader`：从 classpath 读取 `database/schema.sql` 和 `database/seed.sql`，计算稳定指纹。
- `SqlScriptParser`：按 MySQL 语句边界解析脚本，正确处理字符串、反引号和 SQL 注释中的分号。
- `SqlScriptExecutor`：按顺序通过 JDBC 执行解析后的语句，报告失败脚本及语句序号，但不向客户端暴露口令。
- `DatabaseSchemaState`：封装当前指纹、安装时间和目标数据库目录等元数据。

`ServerMain` 在创建并启动 `VCampusServer` 前执行数据库引导。`VCampusServer` 和现有 Repository 继续通过 `ConnectionFactory` 访问数据库，客户端及公共协议不需要增加数据库相关动作。

## 5. 数据库元数据

在 `database/schema.sql` 中加入单行元数据表，并新增对应的 `database/migrations/015_database_bootstrap.sql` 供文档、人工排查和数据库结构历史使用：

```text
vcampus_schema_state
├─ singleton_id       TINYINT，固定为 1
├─ script_fingerprint CHAR(64)，完整 SQL 脚本组合 SHA-256
└─ installed_at       TIMESTAMP，最近一次成功重建时间
```

表中的指纹只能在 `schema.sql` 与 `seed.sql` 全部成功执行后写入。运行时不依赖 001—015 迁移脚本完成自动升级；历史迁移脚本继续保留用于审计和开发者理解结构演进。

## 6. 自动重建流程

1. `ServerMain` 读取现有 `VCAMPUS_DB_URL`、`VCAMPUS_DB_USER`、`VCAMPUS_DB_PASSWORD`。
2. 使用同一连接建立数据库会话并取得 MySQL 命名锁 `vcampus_schema_bootstrap`；等待超时则终止启动。
3. 从 classpath 读取 `schema.sql` 和 `seed.sql`，计算组合指纹。
4. 查询 `vcampus_schema_state`。表不存在、记录缺失或指纹不一致均视为数据库过旧。
5. 如果数据库已是最新版本，释放锁并继续启动。
6. 如果数据库过旧，临时关闭当前会话的外键检查，只删除当前规范 `schema.sql` 声明的 VCampus 表，随后恢复外键检查。
7. 顺序执行完整 `schema.sql` 和 `seed.sql`。
8. 写入本次脚本指纹和安装时间，再读取关键表与元数据进行最小验收。
9. 释放命名锁，启动 Socket 服务。

删除范围必须从受控的规范表清单得到，并对标识符进行反引号转义；不得执行 `DROP DATABASE`，也不得删除同一 schema 内无法确认属于 VCampus 的其他表。即使运行中发生异常，也要在 `finally` 中恢复外键检查并释放命名锁。

## 7. 配置和权限

自动重建继续使用现有数据库连接环境变量，不增加默认密码。连接 URL 必须指向已经存在的 MySQL 数据库；本次不负责创建 MySQL 服务或账号。

用于启动服务端的 MySQL 账号需要对 VCampus 自有表拥有读取、建表、删表、修改结构、建立索引和写入数据所需权限。权限不足时，服务端输出缺失 DDL 权限的说明并终止，不退回到可能不兼容的旧结构继续运行。

为防止误操作，自动重建仅在当前 JDBC catalog 与 URL 指定 catalog 一致时进行。无法确定当前 catalog、连接到系统数据库，或规范表清单为空时一律拒绝重建。

## 8. SQL 解析与执行约束

当前规范脚本包含 `USE`、`PREPARE`、`EXECUTE`、`DEALLOCATE PREPARE`、字符串中的 SQL 片段及普通注释。解析器必须：

- 只在不处于单引号、双引号、反引号、行注释或块注释时将分号视为语句结束。
- 保留字符串和反引号中的原始字符。
- 忽略空语句与纯注释语句。
- 不使用 MySQL 命令行工具，也不依赖 Java 原生对象序列化。
- 发生错误时记录脚本名称和从 1 开始的语句序号，日志中不打印数据库密码。

若未来 SQL 引入存储过程和 `DELIMITER` 指令，应先扩展解析器并补充测试；本次实现只覆盖仓库现有规范脚本实际使用的语法。

## 9. 故障处理与恢复

- 无法连接 MySQL：终止启动并提示检查 URL、账号、密码和 MySQL 服务状态。
- 无 DDL 权限：终止启动并提示为服务端账号授予 VCampus 表结构权限。
- 无法取得命名锁：终止启动，避免两个进程并发重建。
- SQL 解析失败：终止启动并指出脚本和位置，不执行后续语句。
- SQL 执行失败：恢复外键检查、释放锁并终止启动；因为成功指纹未写入，下次启动会重新清理并重建。
- 重建后验收失败：不启动 Socket 服务，下次启动重新执行。

MySQL DDL 通常会隐式提交，因此不能宣称整个重建具备事务原子性。可靠性来自“成功指纹最后写入、失败时拒绝启动、下次重新从清理阶段开始”。

## 10. 测试与验收

### 10.1 自动化测试

- 解析器正确处理注释、引号、反引号和字符串中的分号。
- 规范 `schema.sql`、`seed.sql` 能被完整解析且不产生空语句。
- 指纹对相同内容稳定，任一脚本内容变化都会改变指纹。
- 元数据不存在时进入重建流程。
- 指纹一致时不删除表、不执行 schema/seed。
- 指纹不一致时只删除受控的 VCampus 表，然后依次执行 schema、seed 并最后写入状态。
- 任一步骤失败时不启动服务、恢复外键检查并释放命名锁。
- 并发启动时只有持锁者执行重建。
- 服务端构建产物包含两份规范 SQL 资源。

### 10.2 集成验收

1. 使用旧版数据库启动新版服务端，确认自动重建并可用演示账号登录。
2. 第二次启动同一版本，确认跳过重建且不会重复播种。
3. 修改测试用规范脚本后启动，确认指纹变化会触发一次重建。
4. 使用缺少 DDL 权限的账号启动，确认服务端拒绝运行且错误清晰。
5. 启动两个服务端实例，确认不会并发执行重建。
6. 在根目录执行 `mvn clean verify`，要求所有模块测试通过。

## 11. GitHub 交付纪律

- 现有未提交数据库和测试改动先逐项审查，不与运行时数据混合提交。
- 将 `vcampus-server/data/` 加入 `.gitignore`，不上传本地商品图片和临时文件。
- 数据库自动重建功能、相关测试、SQL 结构和 README 在逻辑清晰的提交中交付。
- 推送前展示最终 `git status`、提交列表、测试结果及相对远端的差异。
- 只有用户明确确认最终待推送内容后，才向 `origin/main` 推送。

## 12. 完成标准

满足以下条件才视为完成：

- 同学已有 MySQL 和可用 VCampus 数据库连接账号。
- 拉取最新版后无需手动执行任何 SQL。
- 第一次启动新版服务端会在必要时自动重建数据库并导入演示数据。
- 后续启动同一版本不会清空数据库。
- 数据库与代码不匹配或自动重建失败时，服务端不会带病启动。
- 客户端仍只通过 Socket 访问服务端。
- 全量 Maven 验证通过，运行时数据与数据库口令未进入 Git。
