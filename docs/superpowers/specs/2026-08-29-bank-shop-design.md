# VCampus 虚拟银行与商店设计

日期：2026-08-29  
状态：设计草案已确认，待文档评审  
范围：虚拟银行、虚拟商店、事务内支付与消息中心联动

## 1. 目标与边界

本阶段完成课程演示所需的虚拟银行与虚拟商店，使学生、教师能够管理虚拟余额、转账、购物和查看订单，使业务管理员能够管理账户、充值、商品、库存和订单。继续遵守 MySQL → 应用服务器 → Swing 客户端三层架构，客户端不得直接连接数据库。

本轮包含：

- 按需自动开立一名用户一个虚拟银行账户；
- 余额、管理员充值、账户冻结与解冻、用户转账和不可修改流水；
- 商品浏览、服务端购物车、订单、库存和管理员管理；
- 使用虚拟银行余额进行商店支付；
- 发货前取消订单时原路退款并恢复库存；
- 银行与商店事件进入消息中心；
- 所有余额、库存、订单和流水变更使用数据库事务。

本轮不包含真实支付渠道、提现、利息、贷款、银行卡、手续费、每日限额、优惠券、促销、物流接口、退货售后、商品图片上传、多商户结算和财务会计总账。

## 2. 已确认业务规则

### 2.1 银行账户

有效校园用户在首次进入银行、首次收到转账或银行管理员首次为其充值时按需自动开户。每名用户只能有一个账户，默认余额为 `0.00`，默认状态为 `ACTIVE`。并发开户由数据库唯一约束保证只产生一个账户。

普通用户只能查看本人余额和流水、向其他有效用户转账以及通过商店消费。只有银行管理员和超级管理员能够查询全校账户、充值、冻结和解冻。普通用户不能自行充值。

账户冻结后不能转账或在商店付款，但仍可收款、接受管理员充值并查看余额与流水。管理员可以解冻账户。历史流水不得修改或删除。

### 2.2 转账

转账通过收款人的登录名精确查找，不区分任何客户端传入的用户 ID。金额必须大于零、最多两位小数，不能向自己转账，不收手续费且不设置每日限额。收款用户必须存在且处于启用状态；尚未开户时自动开户。

转账在一个事务中按账户 ID 从小到大锁定双方账户，完成付款方扣款、收款方入账以及两条共享业务编号的关联流水。任何一步失败都整体回滚。

### 2.3 商品与购物车

商品保存唯一货号、名称、说明、当前价格、库存和上下架状态。已产生订单的商品不得物理删除，只能下架。首版不上传商品图片，客户端使用统一占位图。

购物车保存在服务端数据库并与用户绑定，退出或更换客户端后仍然保留。购物车只保存商品和数量，不保存价格。客户端展示的总价是预估值；结算时服务端必须重新读取并锁定最新商品、价格和库存。商品下架后仍可显示在购物车中，但不能结算。

### 2.4 订单

结算采用即时支付，不保留待付款订单。余额不足、账户冻结、商品下架或库存不足时不创建订单。成功结算后订单直接进入 `PAID`。

订单状态流转为：

```text
PAID
├─ 用户取消 → CANCELLED（退款并恢复库存）
└─ 管理员发货 → SHIPPED
                 └─ 用户确认收货 → COMPLETED
```

只有 `PAID` 订单可取消。取消订单时，状态更新、银行退款、退款流水和库存恢复必须全部成功或全部回滚。首版不提供发货后的退货和退款。

订单项保存下单时的货号、商品名称、单价、数量和小计快照，商品后续改名或调价不得改变历史订单。

## 3. 数据库设计

### 3.1 银行表

`bank_accounts`：

- `id BIGINT` 主键；
- `user_id BIGINT NOT NULL UNIQUE`，关联 `users.id`；
- `balance DECIMAL(15,2) NOT NULL DEFAULT 0.00`，检查余额不小于零；
- `status VARCHAR(16) NOT NULL`，只允许 `ACTIVE`、`FROZEN`；
- `created_at`、`updated_at`。

`bank_ledger_entries`：

- `id BIGINT` 主键；
- `account_id BIGINT NOT NULL`；
- `entry_type VARCHAR(32) NOT NULL`：`ADMIN_TOPUP`、`TRANSFER_OUT`、`TRANSFER_IN`、`SHOP_PAYMENT`、`SHOP_REFUND`；
- `direction VARCHAR(8) NOT NULL`：`DEBIT` 或 `CREDIT`；
- `amount DECIMAL(15,2) NOT NULL`，始终为正数；
- `balance_after DECIMAL(15,2) NOT NULL`；
- `reference_no VARCHAR(64) NOT NULL`，标识同一次业务；
- `counterparty_user_id BIGINT NULL`；
- `operator_user_id BIGINT NULL`；
- `description VARCHAR(255) NOT NULL`；
- `created_at`；
- 唯一约束 `(account_id, entry_type, reference_no)`，防止同一业务重复入账。

应用代码不提供流水更新或删除方法。

### 3.2 商店表

`shop_products`：货号、名称、说明、`DECIMAL(15,2)` 价格、非负库存、上下架状态和时间字段。

`shop_cart_items`：`user_id`、`product_id`、正整数数量和更新时间，`(user_id, product_id)` 为主键。

`shop_orders`：唯一订单号、购买人、唯一结算操作编号、`DECIMAL(15,2)` 总金额、状态、创建时间、发货时间、完成时间和取消时间。结算操作编号用于在客户端未收到响应而重试时定位原订单。

`shop_order_items`：订单、商品 ID、货号快照、名称快照、单价、数量和小计。

`shop_inventory_movements`：商品、变动类型、数量增减值、变动后库存、关联订单、操作者、原因和创建时间。类型包括 `INITIAL`、`ADMIN_ADJUST`、`SALE`、`ORDER_CANCEL`；记录不得修改或删除。

### 3.3 脚本与演示数据

最新版 `database/schema.sql` 包含全部新表和约束，并保持可重复执行。已有数据库分别使用：

- `database/migrations/007_bank.sql`；
- `database/migrations/008_shop.sql`。

`database/seed.sql` 添加脱敏商品和演示账户余额。种子数据必须幂等，不包含真实个人数据或数据库凭据。

## 4. 服务端结构与事务接口

公共协议和枚举放在 `vcampus-common`，数据库与业务实现放在 `vcampus-server`，Swing 页面和网络调用放在 `vcampus-client`。

银行服务端组件：

- `BankStore`：账户、流水、转账和管理员操作接口；
- `BankRepository`：JDBC 实现及银行独立事务；
- `BankPaymentWriter`：允许商店在现有 `Connection` 中扣款或退款；
- `BankService`：会话、权限、输入校验和响应转换。

商店服务端组件：

- `ShopStore`：商品、购物车、订单和管理员接口；
- `ShopRepository`：JDBC 实现并负责结算、取消事务；
- `ShopService`：会话、权限、输入校验和响应转换。

生产环境由 `VCampusServer` 将同一个银行事务写入器注入 `ShopRepository`，方式与现有 `NotificationWriter` 类似。商店不能直接拼接银行 SQL，也不能通过第二个 Socket 请求补扣款。

`BankPaymentWriter` 至少提供：

- 在调用方事务中按用户锁定账户并执行商店扣款；
- 在调用方事务中执行订单退款；
- 写入支付或退款流水；
- 对相同业务编号保持幂等。

## 5. 核心事务流程

### 5.1 商店结算

1. 根据当前会话获取购买人，不接受客户端指定购买人；
2. 检查结算操作编号；若已经成功处理，直接返回对应的原订单；
3. 在事务开始时生成订单号，后续银行流水、库存变动和订单记录共同引用该订单号；
4. 锁定并读取购物车；
5. 按商品 ID 升序锁定商品，校验上下架和库存；
6. 使用数据库价格重新计算每项小计和总额；
7. 锁定购买人的银行账户，校验 `ACTIVE` 和余额；
8. 扣款并写 `SHOP_PAYMENT` 流水；
9. 扣减库存并写 `SALE` 库存变动；
10. 创建带唯一结算操作编号的订单与订单项快照；
11. 清空已结算购物车；
12. 提交事务。

任一步失败时回滚账户余额、银行流水、库存、库存变动、订单、订单项和购物车修改。

### 5.2 取消订单

1. 锁定订单并校验购买人和 `PAID` 状态；
2. 按商品 ID 升序锁定订单商品；
3. 锁定购买人账户；
4. 恢复库存并写 `ORDER_CANCEL` 库存变动；
5. 退款并写 `SHOP_REFUND` 流水；
6. 将订单更新为 `CANCELLED`；
7. 提交事务。

账户后来被冻结不影响退款入账。

### 5.3 防并发与重复提交

转账按账户 ID 升序加锁，结算和取消按商品 ID 升序加锁，减少死锁。余额和库存都在持锁后校验，不能只依赖客户端预检。

转账、充值和结算请求携带由客户端在一次按钮操作开始时生成的 UUID `operationId`；网络重试必须复用该值，新的人工操作必须生成新值。服务端不接受空值或格式非法的操作编号。转账和充值以该编号作为关联流水的 `reference_no`，结算则同时写入订单的唯一结算操作编号，并以预先生成的订单号关联支付流水。

取消订单每个订单只允许成功一次，退款业务编号由服务端按订单号确定性生成，因此重试不会重复退款。客户端按钮在请求期间禁用，数据库唯一约束作为最终防线。重复请求应返回已存在的转账、充值或订单结果；无法安全还原原结果时返回明确的“该业务已经处理，请勿重复提交”，不得再次扣款、退款或变更库存。

## 6. 公共协议

动作前缀：

- 银行：`bank.account.get`、`bank.transfer.create`、`bank.ledger.search`、`bank.admin.account.search`、`bank.admin.topup`、`bank.admin.freeze`、`bank.admin.unfreeze`；
- 商店：`shop.product.search`、`shop.cart.get`、`shop.cart.setQuantity`、`shop.cart.remove`、`shop.checkout`、`shop.order.search`、`shop.order.get`、`shop.order.cancel`、`shop.order.confirm`、`shop.admin.product.save`、`shop.admin.product.setEnabled`、`shop.admin.inventory.adjust`、`shop.admin.order.search`、`shop.admin.order.ship`。

共享枚举包括账户状态、流水类型、流水方向、订单状态和库存变动类型。金额通过协议字符串传输，在服务端解析为 `BigDecimal`；拒绝科学计数法、非数字、非正数、超过两位小数和超过字段上限的值。`bank.transfer.create`、`bank.admin.topup` 和 `shop.checkout` 的请求体必须包含 `operationId`。

## 7. 权限与安全

- 普通用户只能查看和操作本人账户、购物车及订单；
- `BANK_ADMIN` 和超级管理员可以查询账户、充值、冻结、解冻和查看全量流水；
- `SHOP_ADMIN` 和超级管理员可以管理商品、库存和订单发货；
- 商店管理员不能直接操作银行余额；
- 银行管理员不能修改库存或订单；
- 所有用户身份来自服务端会话，忽略客户端伪造的用户 ID；
- 所有 SQL 使用参数化语句；
- 客户端不依赖 JDBC；
- 余额、库存、历史流水和库存变动不允许出现负数或被物理删除。

## 8. Swing 客户端

`BankModulePanel`：

- 普通用户页签：账户首页、转账、流水明细；
- 管理员页签：账户管理、充值与冻结、全量流水；
- 冻结账户禁用转账按钮并显示原因。

`ShopModulePanel`：

- 普通用户页签：商品列表、购物车、我的订单；
- 管理员页签：商品管理、订单管理；
- 商品列表支持搜索、分页、库存状态和加入购物车；
- 购物车支持修改数量、删除和结算；
- 订单支持查看快照、取消未发货订单和确认收货；
- 管理员支持商品新增/修改/上下架、库存调整和发货。

所有网络和数据库工作不得阻塞 Swing EDT。请求期间禁用触发按钮，完成后在 EDT 更新组件。查询、刷新和主要按钮继续使用浅色背景、黑色粗体文字。

## 9. 消息中心联动

新增来源 `BANK`、`SHOP`，新增目标 `BANK_LEDGER`、`SHOP_ORDERS`。建议通知类型：

- `BANK_TRANSFER_RECEIVED`：收到他人转账；
- `BANK_ACCOUNT_TOPPED_UP`：管理员充值；
- `BANK_ACCOUNT_STATUS_CHANGED`：冻结或解冻；
- `SHOP_ORDER_SHIPPED`：订单发货。

用户主动转账、购物、取消订单和确认收货不通知自己。通知写入必须复用当前业务事务中的 `Connection`；通知失败时对应业务整体回滚。消息正文不得暴露账户凭据，只展示必要金额、对方显示名、订单号和操作说明。

## 10. 错误处理

服务端返回稳定、可读的中文消息，包括：

- “账户已冻结，不能转账”；
- “余额不足”；
- “收款用户不存在或已停用”；
- “商品已下架”；
- “库存不足，当前仅剩 N 件”；
- “订单状态已变化，请刷新后重试”；
- “该业务已经处理，请勿重复提交”。

数据库异常不得把表名、SQL、密码或堆栈返回客户端。并发冲突在可以安全重试时返回刷新提示；不自动重放可能造成资金变化的请求。

## 11. 测试与验收

自动化测试至少覆盖：

- 协议动作、枚举和金额解析兼容性；
- 按需开户与并发唯一性；
- 转账、管理员充值、冻结/解冻和权限检查；
- 转账失败时余额和流水整体回滚；
- 两个并发付款请求争用同一余额时不能超支；
- 购物车持久化和服务端重新计价；
- 并发购买最后库存时只允许一个订单成功；
- 结算任一步失败时余额、流水、库存、订单和购物车整体回滚；
- 取消订单的退款、库存恢复和状态原子性；
- 重复业务编号不重复扣款或退款；
- 消息中心来源筛选和业务深链；
- Swing 页面导航、按钮状态和数据显示；
- 根目录 `mvn clean verify`；
- 客户端源码不出现 JDBC 引用。

人工验收使用两个普通客户端和一个管理员客户端，验证开户、充值、转账、冻结、收款、购物车、余额不足、并发最后库存、下单、取消退款、发货、确认收货、流水、库存变动、通知与权限隔离。

## 12. 实施顺序

1. 公共金额规则、银行枚举和数据库迁移；
2. 银行账户、流水、充值、冻结和转账；
3. 银行 Swing 页面和通知；
4. 商店商品、库存和购物车；
5. 商店订单与管理员发货；
6. 事务内银行支付和取消退款；
7. 商店 Swing 页面和通知；
8. 文档、全量自动化验证和 MySQL 双客户端验收。
