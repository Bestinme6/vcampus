# Forum Images, Reports, and Comment Moderation Design

## Goal

Extend the JavaFX forum so a post can contain up to three images, users can report posts and comments, and forum administrators can delete a selected comment. The work must preserve the existing MySQL → application server → JavaFX client flow and the length-prefixed `MessageCodec` protocol.

## Scope

This upgrade includes:

- JPG, PNG, and WebP images on posts, with preview, ordering, upload progress, thumbnail display, and full-size viewing.
- Reports for posts and comments, with fixed reasons and optional details.
- A report queue for forum administrators, with dismiss, hide, and delete outcomes.
- A complete administrator comment-delete path in post detail and content administration.

Comments do not accept images. Reports do not automatically hide content. Physical deletion of forum content is out of scope; existing `DELETED` soft deletion remains authoritative.

## Existing Context and Confirmed Defect

The current forum already has JavaFX feed, editor, detail, moderation, likes, bookmarks, comments, replies, and moderation logs. The shop module has a production file-backed chunked image flow, but it is strongly shop-specific.

Administrator comment deletion currently fails for three connected reasons:

1. `ForumRepository.deleteComment(..., administrator)` ignores the administrator argument and still requires the actor to own the comment.
2. Comment DTO construction sets `canDelete` only when the viewer owns the comment, even when the viewer is a forum administrator.
3. `ForumAdminView` offers hide and restore for comments, but no delete action.

The upgrade will correct all three boundaries and add regression coverage.

## Architecture

### Forum image subsystem

Add a forum-specific `ForumImageStore` under `vcampus-server`. Its default root is `data/forum-images`, configurable through environment variables. It follows the proven shop image flow but does not change or depend on shop storage classes.

The store owns upload sessions, chunk order, size accounting, image decoding, normalized output, thumbnails, content hashes, staged-file cleanup, and ranged reads. A completed upload produces an opaque staged image key bound to the authenticated uploader. It is not publicly readable until a post transaction binds it.

The server accepts declared JPG/JPEG, PNG, and WebP input only after checking magic bytes and decoding the complete image. WebP is decoded server-side through a pure Java ImageIO provider and normalized to a JavaFX-readable output; stored originals and thumbnails are therefore JPG or PNG. Metadata and alpha-bearing images use PNG; other images use JPEG. Image dimensions and decoded pixel count have explicit limits to prevent decompression bombs.

Completed, unbound files are garbage-collected after an expiry period. Bound files remain while their post image row exists. Post deletion makes images inaccessible immediately; file cleanup may run after the database transaction and is retried if the filesystem operation fails.

### Database

Add `forum_post_images` with:

- `id` as the public image identifier.
- `post_id` foreign key to `forum_posts`.
- `storage_key`, generated by the server and never supplied as a filesystem path.
- `position`, constrained to 0–2 and unique within a post.
- `mime_type`, `byte_size`, `width`, `height`, and `created_at`.
- Indexes for ordered post lookup and storage cleanup.

Add `forum_reports` with:

- Reporter, `target_type` (`POST` or `COMMENT`), and target ID.
- Reason enum, optional detail up to 300 characters, and creation time.
- Status (`PENDING`, `DISMISSED`, or `ACTIONED`).
- Resolution action, administrator, note, and handled time.
- A unique key on reporter, target type, and target ID, enforcing one report per user for a given item.
- Indexes for pending queue order, target lookup, and administrator history.

Schema creation and safe rerunnable upgrade SQL live together in `database/schema.sql`. Repository tests use matching H2 table definitions.

### Protocol and shared models

Add shared enums and records in `vcampus-common` for image metadata, report target, report reason, report status, and resolution action. All new action names use the `forum.` prefix.

Image actions cover upload start, chunk append, upload completion, metadata lookup, thumbnail read, and full-image ranged read. Upload requests carry Base64-encoded chunks within the existing binary message payload and enforce conservative chunk sizes below the codec frame limit.

Forum post creation accepts zero to three completed staged image keys in display order. Post detail returns ordered image metadata; bytes are fetched lazily.

Report actions cover create, current-user state lookup, administrator search, and administrator resolution. Every service method authenticates independently and validates target visibility and role permissions.

## User Flows

### Creating a post with images

The editor adds an image area below the body. A user may choose at most three files. Each selection shows a local thumbnail, size, remove control, and left/right ordering controls. Local validation rejects unsupported types and oversize files before network work begins.

Publishing performs the following sequence off the JavaFX thread:

1. Upload selected images in their displayed order and report aggregate progress.
2. Complete and validate each upload, receiving staged image keys.
3. Create the post with title, body, section, and ordered keys.
4. Navigate to the new post only after the server has committed the post and bindings.

The editor is locked while publishing. On failure, title, body, and local selections stay intact. The user can retry. Reusing an already completed key is idempotent for the same user and create attempt; it cannot be bound to multiple posts.

### Viewing post images

Post detail renders thumbnails beneath the text in database order. Images load asynchronously and cache by image ID. Clicking a thumbnail opens a styled modal with the full image scaled to the available window while preserving aspect ratio. A failed image shows a placeholder and retry control without hiding the post text or comments.

Image reads require a visible, enabled post for ordinary users. Forum administrators may read images while reviewing hidden content. Deleted content images are unavailable through normal detail requests.

### Reporting content

Normal visible posts and comments show a Report action unless the current user authored the target. The dialog offers:

- Advertising or spam
- Abuse or harassment
- False or misleading content
- Privacy disclosure
- Illegal or inappropriate content
- Other

Optional details accept up to 300 characters. Submission does not change content visibility. A successful submission replaces the action with a disabled `Reported` state. Duplicate reports, self-reports, missing targets, and reports against hidden or deleted content receive specific errors.

### Administrator report queue

`ForumAdminView` gains a `Reports` tab. It filters by pending/processed state, target type, and reason. Selecting a row shows the reported content snapshot, current target state, reporter, reason, details, and timestamps.

Pending reports support:

- Dismiss report: content stays unchanged.
- Hide content: target becomes `HIDDEN`.
- Delete content: target becomes `DELETED`.

Each resolution requires a 2–255 character administrator note. A conditional status update ensures only one administrator can resolve a pending report. A stale client receives a conflict response and reloads the current record. Hide and delete outcomes update the content and report in one database transaction and append the existing moderation log.

### Administrator comment deletion

Forum administrators see Delete on every normal comment in post detail and when a comment is selected in content administration. Deletion requires a reason in administrative contexts, soft-deletes the comment, refreshes post comment statistics, and adds a moderation log. Authors retain their existing self-delete flow without an administrative reason.

Deleting or hiding a reported target resolves all still-pending reports for that target as actioned, referencing the administrator action. Dismissing one report affects only that report.

## Validation and Security

- Maximum three images per post and 5 MiB per input image; limits are enforced in client, service, and store layers.
- File extension and declared MIME are hints only. Magic-byte inspection, full decoding, pixel limits, and normalized re-encoding determine acceptance.
- Upload IDs and staged keys are opaque, unpredictable, owned by one authenticated user, and expire.
- Paths are generated and resolved under the configured forum image root; client input never becomes a filesystem path.
- Chunk sequence, declared total, actual total, and content digest are verified before completion.
- Image network and filesystem work stays off the JavaFX thread; UI mutations stay on it.
- Users cannot report themselves or inaccessible content. Forum administrator authorization is checked by the server for every queue and resolution request.
- Report uniqueness is enforced by the database, and resolution uses a transaction with a pending-state predicate.
- User-visible records never expose absolute paths, uploader tokens, or another user's private session data.

## Error Handling and Recovery

Upload errors use stable codes for unsupported image, oversize image, invalid dimensions, invalid chunk order, ownership mismatch, expired upload, quota exhaustion, and storage failure. The client maps them to concise Chinese messages and preserves editor state.

Filesystem and database operations cannot share one transaction. Completed image blobs are written before the database binding transaction and remain staged until referenced. A failed post transaction therefore leaves only an expiring unbound blob. After a successful transaction, the binding is authoritative; cleanup jobs reconcile orphaned staged files and deleted-post files.

Report creation maps duplicate, self-report, invisible target, and missing target conditions separately. Report resolution maps stale status to conflict and forces a queue refresh.

## Testing

Automated coverage includes:

- `MessageCodec` round trips and frame bounds for image chunks and report parameters.
- Forum image store tests for JPG, PNG, WebP normalization, MIME mismatch, pixel and byte limits, chunk ordering, ownership, expiry, ranged reads, cleanup, and path containment.
- Repository tests for ordered image binding, maximum count, post rollback, report uniqueness, self-report rejection, visibility checks, queue filters, atomic resolution, moderation logs, and concurrent resolution.
- Service permission tests for ordinary users, forum administrators, invalid sessions, and cross-user staged keys.
- Regression tests proving an administrator can delete another user's selected comment from detail and administration while a normal user cannot.
- JavaFX editor, gallery, report dialog, report queue, progress, retry, and Event Dispatch/JavaFX thread behavior tests.
- Forum visual captures at the established content widths, followed by the root `mvn clean verify` command.

## Documentation and Configuration

Update `docs/requirements.md` when implementation status changes. Document the forum image root, size, pixel, chunk, staging expiry, and storage quota environment variables in the README. No database password, token, real personal data, or machine-specific absolute path is committed.

## Acceptance Criteria

The feature is accepted when a user can publish a post with zero to three supported images, see the ordered gallery after reconnecting, report another user's visible post or comment once, and see a clear reported state. A forum administrator can filter and resolve reports, hide or soft-delete their targets with an audit record, and delete any selected normal comment from both relevant administrator surfaces. Invalid files, unauthorized requests, duplicates, races, and partial failures leave consistent database and filesystem state, and the full Maven verification succeeds.
