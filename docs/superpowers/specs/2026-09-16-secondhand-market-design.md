# 校园二手市场设计

- 日期：2026-09-16
- 状态：交互方案已确认，等待书面规格复核
- 范围：普通用户发布二手物品、按收货地址交付、虚拟余额暂存与结算、交易评价及管理员治理

## 1. 目标与边界

在现有校园商店内增加“二手市场”入口。学生、教师等已登录用户可以成为卖家，发布并管理自己的单件二手物品，购买他人物品，并对自己的订单标记交付；买家确认收货后，卖家获得虚拟银行款项。每笔完成的交易允许买家评价一次，评分汇总为卖家信誉。

二手市场在用户界面上属于商店，在业务与数据上保持独立。继续遵守 MySQL → 应用服务器 → 客户端的三层架构、`MessageCodec` 长度前缀协议、服务端会话权限校验和 JavaFX 线程规则。原校园商店的商品、订单、评价和管理员权限不因本功能改变。

本期不接入真实支付、快递公司、物流单号、聊天、议价、拍卖、自动确认收货或自动放款。结算必须使用商店共用的收货地址；交付由双方线下完成，系统只记录卖家“已交付”和买家“确认收货”的状态。地址簿、下单地址快照与查看权限遵循[商店共用收货地址设计](2026-09-16-shop-shipping-addresses-design.md)。虚拟余额暂存是系统内部记账，不代表真实金融托管。

## 2. 方案选择

1. **采用：商店内独立子业务。** `ShopView` 增加“二手市场”入口；二手商品、订单、暂存款和评价使用独立服务及表，底层复用图片、虚拟银行、通知和界面组件。用户入口统一，权限与资金规则清晰。
2. 独立顶层模块：隔离充分，但重复导航、页面、客户端网络和商店基础设施，不利于课程演示。
3. 在原商店表上增加商品类型和卖家 ID：短期改动看似少，但原商品由管理员管理、原订单由管理员发货，容易让普通卖家继承不应有的权限，并混淆两种结算规则。

## 3. 角色、页面与物品

- 所有已登录校园用户可浏览二手市场、发布物品及购买他人的物品；不能购买自己的物品。
- 卖家只能编辑、下架自己的未成交物品，只能查看和标记自己订单的交付。服务端从会话取得卖家 ID；客户端传入的用户 ID 不作为授权依据。
- 商店管理员和超级管理员可检索、隐藏或恢复违规物品，查看二手订单与暂存款，并以填写原因、保留审计记录的方式处理异常订单。普通卖家不获得原商店管理员权限。
- 商店页面提供“校园商店 / 二手市场”切换。二手区域提供“逛二手、发布物品、我的出售、我的购买”；管理入口只对管理员显示。
- 物品保存标题、描述、类别、成色、价格、卖家和最多五张图片。每条物品数量固定为一，不引入普通商店的库存调整和购物车批量结算。
- 发布后立即公开；管理员可因违规隐藏。物品下架或隐藏后不能新购，但历史订单及其商品快照继续可见。已被管理员隐藏的物品不能由卖家自行重新公开。
- 购买时买家必须选择本人已保存的收货地址或填写一次性地址；地址簿与普通商店共用，每人最多保存三条。二手卖家只能在订单支付成功后，通过自己订单的详情查看该订单的完整收货地址，不能浏览买家的地址簿。

## 4. 订单与资金状态

| 事件 | 订单 | 物品可售性 | 虚拟银行与暂存款 |
| --- | --- | --- | --- |
| 买家购买 | `PAID` | 锁定为不可售 | 同事务扣买家余额并建立等额 `HELD` 暂存记录 |
| 买家在交付前取消 | `CANCELLED` | 若物品未下架或隐藏，恢复可售 | 同事务将暂存款退还买家，暂存状态为 `REFUNDED` |
| 卖家标记校内交付 | `SHIPPED` | 保持不可售 | 不转移款项；通知买家确认 |
| 买家确认收货 | `COMPLETED` | 保持已售 | 同事务将暂存款计入卖家余额，暂存状态为 `SETTLED` |

购买时在数据库事务内锁定物品并再次检查状态、价格和卖家，保证并发请求只有一个买家成功。买家支付额、订单价和结算额均使用 `DECIMAL(15,2)` / `BigDecimal`，订单保留购买时的标题、价格、成色、卖家和收货地址快照。每次购买有客户端生成的 UUID 业务编号和数据库唯一约束；重试必须返回同一订单，不得重复扣款或因地址簿变化而改址。取消、交付、确认也必须幂等。

暂存款使用独立的二手交易负债记录，并为买家扣款、买家退款和卖家入账增加专用银行流水类型；不复用普通商店的 `SHOP_PAYMENT` / `SHOP_REFUND` 类型。订单、暂存记录、余额、流水和通知在同一个 JDBC 事务内更新，任一步失败均回滚。冻结账户不能购买，但可接收退款和卖家入账，沿用现有银行规则。

卖家不能确认收货或自行放款，买家不能替卖家交付。`SHIPPED` 后买家不能自行取消，系统也不会因超时自动给卖家放款。管理员核对异常订单后，可对 `PAID` 订单退款；对 `SHIPPED` 订单可选择退款买家或结算卖家。管理员处理同样更新订单为 `CANCELLED` 或 `COMPLETED`，并要求原因、幂等业务编号和不可变审计记录；结算与退款互斥，不能两边都入账。已交付订单若被退款，不自动重新上架物品，避免把可能已交付的同一件物品再次售出。

## 5. 评价与卖家信誉

- 仅订单买家可在 `COMPLETED` 后对该笔交易评价一次；评价绑定二手订单，不能评价自己的交易，也不能因删除评价重新评价。
- 评价采用 1～5 星、去除首尾空白后 5～1000 字正文、最多三张可选图片；作者可编辑正常评价或软删除。其他用户可给正常评价点“有帮助”，不能点赞自己的评价。
- 正常评价展示在相关交易/物品记录及卖家历史评价中。卖家公开的平均分、评价数和星级分布只统计正常评价；新卖家显示“暂无评价”。单件物品不计算无意义的多次购买平均分。
- 管理员可填写原因隐藏或恢复违规评价，保留审核日志；隐藏、删除评价不参与卖家信誉。评价图片、点赞和审核规则参照现有商店实现，但二手评价使用独立数据与权限边界。

## 6. 技术分层与数据

### `vcampus-common`

新增二手物品、订单、暂存及评价状态所需共享模型与 `shop.used.*` 动作。协议只传业务 ID、操作编号和用户输入；卖家、买家、订单金额、评价资格、评分汇总等服务端事实不能由客户端指定。继续使用 `MessageCodec` / `RowCodec`，不使用 Java 原生序列化。

### `vcampus-server`

新增独立的二手市场服务、仓储和交易评价服务；复用现有图片校验/缩略图能力，但使用二手物品与评价专用存储目录和元数据。扩展银行事务写入接口以支持二手扣款、退款与卖家入账；`RequestRouter` 路由 `shop.used.*`，所有写操作在服务端校验会话并在事务内复核归属和状态。通知买卖双方支付、取消、交付、确认和管理员处理结果。

数据库通过新迁移与 `database/schema.sql` 同步增加二手物品、图片、订单、暂存款、评价、评价图片、点赞和审核日志。二手订单含收货地址快照，复用共享地址簿而不复制地址管理表。物品状态锁保证同一时刻至多一笔有效交易；取消后可重新出售，因此历史上允许同一物品对应多笔已取消订单。外键与唯一约束保障订单一笔暂存款、每单一条评价及业务编号幂等。历史订单不依赖可变物品或地址簿信息展示。

### `vcampus-client`

在原生 JavaFX 商店中增加二手市场入口和独立页面/网关；复用商品卡片、图片上传与评价交互的视觉组件，但普通卖家的操作与管理员操作分开。Socket、图片及数据库相关等待都在后台线程，界面更新回到 JavaFX 应用线程。旧 Swing 商店保持兼容，不在本期扩展完整二手界面。

## 7. 错误处理与验收

- 余额不足、冻结、购买自己的物品、商品已售或已隐藏、重复购买、越权编辑或发货均返回明确业务错误，且不产生部分订单或部分资金流水。
- 网络响应不确定时用相同业务编号重试；数据库唯一约束和状态条件保证不会重复扣款、退款、结算或通知。
- 图片上传校验格式、大小、像素与归属；物品或评价写入失败时清理可确定未引用的新文件，数据库提交结果不确定时保留文件待核对，避免已提交记录指向被删除的文件。
- 覆盖协议往返、卖家/买家/管理员权限、并发抢购、价格快照、付款与回滚、取消退款、交付后不可自行取消、确认结算、管理员互斥裁决、评价资格和信誉汇总，以及 JavaFX 页面和线程测试。
- 实施时同步更新 `docs/requirements.md`、`docs/shop.md`、数据库迁移与 `database/schema.sql`；根项目以 `mvn clean verify` 验证。
